1. Pwn常用命令

1.1 Pwntools 常用片段

功能说明：

  • 初始化 pwntools 基础环境
  • 装载 libc 符号
  • 计算 system 和 "/bin/sh" 地址
  • 处理常见的地址泄露

使用说明：

  • context(...) 一般写在脚本最前面
  • libc_base 需要你先通过泄露算出来
  • u64(...ljust...) 常用于处理只泄露 6 字节的 amd64 地址

常用点：

  • context(...) 先设架构和日志级别
  • ELF() 读符号、GOT、PLT
  • u64/u32 配合 ljust 处理泄露地址
  • next(libc.search(b'/bin/sh')) 快速找字符串

1.2 ROPgadget

功能说明：

  • 从二进制中快速搜索常用 ROP gadget
  • 适合找寄存器控制、栈迁移、系统调用相关片段

使用说明：

  • 把 文件名 换成目标程序
  • 把 eax 换成你想筛的寄存器或指令关键字
  • amd64 题里常搜 rdi/rsi/rdx/rax/syscall

比赛里常用来快速搜：

  • pop rdi ; ret
  • syscall ; ret
  • 栈迁移 gadget

1.3 GDB / pwndbg 常用

功能说明：

  • 下基于重定位的断点
  • 加载/移除源码路径
  • 加载/移除符号文件

使用说明：

  • b *$rebase(偏移) 适合 PIE 程序
  • directory /usr/src/glibc/ 适合本地看 glibc 源码
  • symbol-file 适合切换到带符号版本二进制

补充习惯：

  • 本地调试优先下 b main
  • 泄露后优先看 vmmap
  • 堆题先看 bins
  • 看 chunk 直接 x/40gx addr

1.4 seccomp / 沙盒

功能说明：

  • 查看目标程序的 seccomp 过滤规则
  • 判断题目允许哪些系统调用

使用说明：

  • 适用于怀疑有沙盒限制的题
  • 比赛里优先确认是否禁用了 execve
  • 如果 execve 被禁，大概率要转 ORW/openat

现场用途：

  • 判断能不能 execve
  • 判断是否只能 open/read/write
  • 判断是否要走 openat

1.5 ctypes 调 libc

功能说明：

  • 在本地 Python 中直接调用 libc 函数
  • 适合做快速测试、校验返回值或理解某些接口行为

使用说明：

  • 主要用于本地实验，不是比赛时 exp 主流程
  • 函数参数类型复杂时，记得额外设置 argtypes/restype

1.6 pwntools 调试接口

attach

功能说明：

  • 将 gdb 附加到一个已经运行中的目标

使用说明：

  • 适合 process() 或 remote 转本地复现后临时附加
  • gdbscript 里可以放断点、命令、自动继续逻辑

debug

功能说明：

  • 直接在 gdb 下启动目标程序

使用说明：

  • 适合本地完整复现题目启动流程
  • 可以传 env、参数、脚本，省去手动开 gdb

debug_assembly

功能说明：

  • 把汇编代码临时打包成可执行文件并启动调试

使用说明：

  • 适合调试短汇编片段、练习 shellcode
  • 输入是汇编文本，不是字节串

debug_shellcode

功能说明：

  • 直接调试已经组装好的 shellcode 字节串

使用说明：

  • 输入是原始字节，不是汇编源码
  • 适合和 asm() 结果联动测试

1.7 process 常见参数

功能说明：

  • 本地起进程并指定参数/环境
  • 关闭 ASLR 方便本地复现和调试

使用说明：

  • 比赛时通常先本地 process() 调通，再切远程
  • aslr=False 只适合本地调试，不代表远程环境

常看能力：

  • p.libs() 看共享库基址
  • p.pid / p.proc.pid 看进程号
  • p.close() / p.kill()

1.8 ELF 常见接口

功能说明：

  • 读取程序符号、GOT、PLT、.bss 等关键地址

使用说明：

  • elf.symbols['puts']、elf.got['puts']、elf.plt['puts'] 是最常见用法
  • elf.bss() 适合找可写段作为缓冲区

1.9 Shellcode 模板

来源：站内 ShellCode

这一节优先整理比赛里最常用、最稳定的两类：

  • ORW/openat + read + write
  • execve("/bin/sh", 0, 0)

比赛里判断方法很简单：

  • 能直接起 shell，就优先 execve
  • execve 被 seccomp 禁掉，就优先 ORW
  • 如果只给了一个已知可读可写地址，就优先把字符串和缓冲区都放在那里

ORW

功能说明：

  • 打开文件、读取内容、写到标准输出
  • 常用于 seccomp 禁 execve 的沙盒题

使用说明：

  • 当前模板是 amd64 syscall 风格
  • 这里实际走的是 openat + read + write
  • 依赖 rsp 指向可读写区域，便于放文件名和读入缓冲区
  • 文件描述符 3 是常见情况，但不是绝对，比赛里要根据返回值调整
  • 0x67616c66 是 "flag" 的小端表示
  • edi = 0x0FFFFFF9C 对应 AT_FDCWD

执行逻辑：

  • 先把 "flag" 压栈
  • 调用 openat(AT_FDCWD, "flag", 0, 0x180)
  • 再调用 read(3, rsp, 0x40)
  • 最后调用 write(1, rsp, 0x40)

适用场景：

  • seccomp 禁止 execve
  • 程序能执行 shellcode，但不能直接交互拿 shell
  • 题目目标就是读 flag

注意点：

  • 文件描述符不一定是 3，有时需要根据返回值改 rdi
  • 目标文件名不一定是 flag，可能是 ./flag、/flag、flag.txt
  • 如果 rsp 不可写，要先想办法把 shellcode 改成使用别的可写地址
  • 如果过滤了 openat，还要改成允许的系统调用组合

execve(“/bin/sh”, 0, 0)

功能说明：

  • 直接执行 /bin/sh
  • 适合无沙盒或沙盒允许 execve 的场景

使用说明：

  • 同样要求栈可写，用于放字符串
  • 若远程没有交互回显，要检查标准输入输出是否正常连通
  • 这是最标准的 amd64 execve("/bin/sh", 0, 0) 版本

执行逻辑：

  • 先把 "/bin/sh" 压栈
  • rdi = rsp 指向字符串
  • rsi = 0、rdx = 0
  • rax = 59 后触发 syscall

适用场景：

  • 没有 seccomp 或 seccomp 没禁 execve
  • 题目环境支持交互式 shell
  • 目标是直接起 shell 再手工翻 flag

注意点：

  • 如果远程是非交互管道环境，起了 shell 也未必好用
  • 如果程序很快退出，要考虑 shell 是否会随父进程结束
  • 如果目标环境是 chroot、容器、只读文件系统，起 shell 不等于立刻拿 flag

变形与现场使用

功能说明：

  • 这部分对应站内原文最后提到的“变形”
  • 核心意思不是换一种语法，而是根据题目的可写地址和约束，把模板改成更适合现场环境的版本

使用说明：

  • 如果你已经拿到一个确定可读可写的地址，那么让 shellcode 使用那块地址往往比硬依赖 rsp 更稳
  • 不管是 "flag" 还是 "/bin/sh"，本质都只是一个字符串指针问题

常见变形方向：

  • 把文件名字符串放到堆上、.bss、mmap 区
  • 把读缓冲区和字符串区域分开，避免覆盖
  • openat 改 open
  • execve 改 execveat
  • 配合 read 先把二阶段 shellcode 读到可执行区域

比赛建议：

  • 先确认“可执行”与“可写”是不是同一块区域
  • 先确认 shellcode 长度限制
  • 先确认过滤的是系统调用，还是仅仅过滤了某几个关键号
  • 如果过滤很重，就不要执着于直接 shellcode，及时切换 ROP + ORW

1.10 堆题 ORW 专题

补充来源：

  • 用户提供文章：https://iyheart.github.io/2025/04/23/CTFblog/PWN%E7%B3%BB%E5%88%97blog/Linux_pwn/2.%E5%A0%86%E7%B3%BB%E5%88%97/PWN%E5%A0%86ORW/
  • 同主题补充资料：CN-SEC: 浅析CTF中PWN题堆类型的ORW技术
  • 同主题补充资料：Anquanke: PWN堆溢出技巧：ORW的解题手法与万金油Gadgets
  • 同主题补充资料：setcontext 实现 ORW 示例

功能说明：

  • 这一节讲的不是普通 ROP ORW
  • 而是“题目核心漏洞发生在堆上，最终因为沙盒或环境限制，落点必须是 ORW”的情况

使用说明：

  • 如果你已经能直接 system("/bin/sh")，通常没必要强行走 ORW
  • 只有在 execve/system/one_gadget 被沙盒、版本或环境卡住时，才把堆链导向 ORW

1.10.1 什么叫堆题 ORW

核心场景：

  • 漏洞本体是堆题：
    UAF、double free、堆溢出、tcache/largebin/IO_FILE
  • 但题目开了沙盒，导致不能直接起 shell
  • 所以最终目标从“控制 RIP 后直接 getshell”变成“控制 RIP 后执行 open/read/write 读 flag”

最短理解：

  • 堆利用负责给你“执行流控制”
  • ORW 负责在受限环境下真正把 flag 读出来

1.10.2 什么时候该从 getshell 切到 ORW

典型信号：

  • seccomp-tools dump 看到禁了 execve
  • prctl(PR_SET_NO_NEW_PRIVS, 1) 或 seccomp 规则明显限制系统调用
  • 远程环境即使起 shell 也不稳定
  • 没法把参数稳定布成 system("/bin/sh")

比赛口诀：

  • 能 shell 就 shell
  • 不能 shell 就 ORW
  • 有 mprotect 就考虑 shellcode ORW
  • 没 mprotect 就考虑 ROP ORW

1.10.3 堆题 ORW 的三层结构

第一层：信息泄露

  • 泄露 libc
  • 泄露 heap
  • 必要时泄露栈或 environ

第二层：执行流控制

  • 覆写 __free_hook / 旧版 __malloc_hook
  • setcontext
  • IO_FILE
  • exit 路径
  • ROP 返回地址

第三层：真正执行 ORW

  • 纯 ROP 调 open/openat -> read -> write
  • mprotect + shellcode
  • setcontext 把寄存器和栈一次性摆好，再跑 ORW

1.10.4 常见入口一：setcontext 打 ORW

功能说明：

  • 这是堆题 ORW 里非常高频的一条路线
  • 尤其适合“我已经能控制一个函数指针，但还要一次性摆很多寄存器”的情况

使用说明：

  • 常见做法是把某个可控调用点改到 setcontext + offset
  • 再在堆上伪造一份上下文，让它恢复寄存器和栈

典型利用链：

  • 先通过堆漏洞拿到 libc/heap leak
  • 再把控制点劫持到 setcontext
  • 把伪造的 ucontext / SigreturnFrame 风格数据放在堆上
  • 最终切到一条 ORW ROP chain 或直接切到 shellcode

优点：

  • 一次能控很多寄存器
  • 很适合 open/read/write 这种多参数调用
  • 对堆题尤其友好，因为伪造上下文天然适合放在堆块里

注意点：

  • setcontext 的可用偏移会因 glibc 版本变化
  • 你需要确认恢复寄存器时到底从哪块内存取值
  • 题解里常见 setcontext+53、setcontext+61 一类偏移，但不能盲抄

1.10.5 常见入口二：mprotect + shellcode ORW

功能说明：

  • 当你能 ROP 但可执行内存不方便，mprotect 是很常见的中间步骤

使用说明：

  • 先用 ROP 调 mprotect(addr, size, PROT_READ | PROT_WRITE | PROT_EXEC)
  • 把某个堆块、.bss 或栈页改成可执行
  • 再跳到前面准备好的 ORW shellcode

典型利用链：

  • 泄露地址
  • 劫持控制流
  • mprotect 改页权限
  • 跳 ORW shellcode

适用场景：

  • 有足够 gadget
  • mprotect 没被过滤
  • shellcode 比长 ROP 更好写

注意点：

  • mprotect 要按页对齐
  • 目标地址最好选你已经有写权限的区域
  • 如果 seccomp 把 mprotect 也禁了，就要回到纯 ROP ORW

1.10.6 常见入口三：纯 ROP ORW

功能说明：

  • 这是最通用的 ORW 方式

使用说明：

  • 找齐 pop rdi、pop rsi、pop rdx，必要时补 pop rax 和 syscall
  • 也可以直接调 libc 里的 open/read/write

标准链路：

  • open("/flag", 0)
  • read(fd, buf, size)
  • write(1, buf, size)

适用场景：

  • mprotect 被禁
  • 不想依赖 shellcode
  • libc 和 gadget 已经足够稳定

注意点：

  • 文件路径要提前放好
  • fd 不一定固定是 3
  • 远程如果路径不是 /flag，要及时改成 flag、./flag 等

1.10.7 堆题里常见的 ORW 载体

可以承载 ORW 的地方通常有这些：

  • 堆上的伪造 ROP chain
  • 堆上的伪造 ucontext
  • 堆上的 shellcode
  • 伪造的 FILE 结构触发出的函数指针链
  • free / exit 时会自动触发的回调路径

最常见的思路转换：

  • 老版本：
    hook -> setcontext -> ORW
  • 高版本：
    largebin/TSU/IO_FILE -> 可控函数指针 -> ORW
  • 有 Apple2/Emma：
    IO_FILE -> mprotect/setcontext -> ORW

1.10.8 堆题 ORW 的现场检查清单

  • 先确认沙盒到底禁了什么
  • 先决定最终是 ROP ORW 还是 shellcode ORW
  • 先找字符串放哪：
    "/flag"、"flag"、"./flag"
  • 先找缓冲区放哪：
    堆、.bss、栈、mmap
  • 先找控制点从哪进：
    hook、setcontext、IO_FILE、返回地址
  • 先确认是否需要页对齐和 mprotect

1.10.9 一条最常见的思维模板

看到堆题 + 沙盒时，可以直接这么想：

  1. 我能不能先泄露 libc/heap
  2. 我能不能拿到一次稳定的函数指针调用
  3. 这个调用更适合转 setcontext，还是直接转 mprotect
  4. 最后 ORW 用 ROP 还是 shellcode

一句话记忆：

  • 堆题 ORW 的本质，不是多了一个新技巧，而是把“堆利用拿到的控制流”改造成“读文件能力”

1.11 线下比赛现场 checklist

  • 先 checksec

  • 能交互优先考虑 system("/bin/sh")
  • 有沙盒优先考虑 ORW

2. glibc攻击手法大全

2.0 比赛速查总表

功能说明：

  • 这一张表不是为了替代细节，而是为了让你在线下比赛时先快速选路线
  • 先根据漏洞类型和 glibc 特征筛一轮，再往下翻具体小节

使用说明：

  • “典型目标”表示这类手法最常见的落点，不代表唯一打法
  • “版本提示”只是比赛中的经验判断，不是绝对边界
攻击方式 常见前提 典型目标 版本提示
fastbin attack UAF / 堆溢出 / 可改 fd 任意分配、栈上分配、伪造结构体 更偏老版本，但新版仍可能作为中间步骤出现

2.0.1 glibc 版本判断习惯

  • 先看有没有 tcache：
    glibc 2.26+ 往往要优先考虑 tcache
  • 再看有没有 safe-linking：
    高版本单链表利用一般要结合 heap leak
  • 再看 hook 还能不能打：
    新版对 __malloc_hook / __free_hook 依赖要明显降低
  • 最后看 IO_FILE 有没有机会：
    当常规 hook 路线走不通时，FSOP/Apple2 很值得想

2.1 堆利用

2.1.1 Unsorted Bin Attack

来源：站内已有《Unsorted bin Attack》。

核心思路：

  • 先把大 chunk 放入 unsorted bin
  • 改写其 bk 为 target_addr - 0x10
  • 再次申请对应大小 chunk
  • 触发 unlink 风格写入，把 main_arena 附近值写到目标位置

适用特点：

  • 常用于一次性任意地址写
  • 多见于老版本 glibc
  • 需要满足 unsorted bin 相关完整性条件

注意点：

  • 若申请大小不匹配，可能触发 malloc 检查并 abort
  • 二次利用时要考虑 main_arena 被污染后的修复问题

2.1.2 Tcache 相关

来源：CTF Wiki / tcache attack

核心原因：

  • tcache 是线程本地缓存
  • 释放和分配路径更短
  • 早期检查相对薄弱，使堆利用重新变得简单

常见利用方向：

  • tcache poisoning
  • tcache dup
  • tcache house of spirit
  • tcache stashing unlink attack

2.1.2.1 Tcache poisoning

核心思路：

  • 释放某个 tcache chunk
  • 改写其 next/fd 指针
  • 之后连续 malloc，把分配结果导向目标地址

适用前提：

  • 能写已释放 chunk 的用户区
  • 目标大小落在 tcache 管理范围内

线下用途：

  • 任意分配到栈
  • 任意分配到 __free_hook/__malloc_hook 附近（旧版本）
  • 任意分配到伪造结构体

2.1.2.2 Tcache dup / double free

核心思路：

  • 同一个 chunk 被重复放入 tcache
  • 导致后续两次分配拿到同一块内存或构造可控链

注意点：

  • 高版本检查更严
  • 比赛里要优先确认是否存在 key 检查或 safe-linking

2.1.2.3 Tcache stashing unlink attack

来源：CTF Wiki / tcache attack

核心思路：

  • 当 tcache 还有空位时，smallbin 中同尺寸 chunk 会被搬运进 tcache
  • 搬运过程中，后续节点的完整性检查不够严格
  • 如果能改 smallbin chunk 的 bk，可造成任意地址写或伪造 chunk 分配

适用场景：

  • 新版环境下 unsorted bin attack 不再好用
  • 题目存在 smallbin、UAF、bk 可控等条件

比赛里怎么识别：

  • 某个尺寸同时和 tcache、smallbin 发生交互
  • 程序允许你多次申请释放同尺寸 chunk
  • 老的 hook 思路被卡住，但你还能改 bin 元数据

2.1.3 Fastbin Attack

来源：CTF Wiki / fastbin attack

利用前提：

  • 漏洞发生在 fastbin chunk
  • 存在堆溢出、UAF 或其他能改 chunk 内容的能力

典型分类：

  • fastbin double free
  • House of Spirit
  • alloc to stack
  • arbitrary alloc

核心直觉：

  • fastbin 用单链表管理空闲块
  • 如果能改链表指针，就能把 malloc 引向你指定的位置

适合比赛时记住的一句话：

  • fastbin attack 本质就是“劫持 fastbin 链表，拿到伪造分配结果”

实战观察点：

  • free 后还能不能 edit/show
  • fake chunk 能不能放在 .bss / 栈 / 可控堆区
  • 程序是否存在对 size 的二次校验

2.1.4 Smallbin / Largebin Attack

2.1.4.1 Smallbin 相关

比赛直觉：

  • smallbin 更强调双向链表和 unlink 过程
  • 许多利用会和 unlink、tcache stashing、largebin 组合出现

当前先作为理解链路保留，后续可继续细化。

2.1.4.2 Largebin Attack

来源：CTF Wiki / large bin attack

核心思路：

  • 利用 unsorted bin -> largebin 入链过程中的检查缺失
  • 特别是 largebin 跳表相关指针的处理逻辑
  • 改写相关指针后，在后续 malloc 过程中实现定向写入

适用特点：

  • 往往需要较大 chunk
  • 更依赖对 bin 迁移过程的理解
  • 常见于高版本 glibc 里替代部分老攻击法

线下建议：

  • 如果题目给了大 chunk、UAF、且 old-school 手法被拦，优先想 largebin

常见利用目标：

  • 覆写某个关键地址附近的指针值
  • 辅助构造下一阶段任意分配
  • 配合 FSOP、函数指针或退出路径利用

2.1.5 Safe-linking 绕过

来源：CTF Wiki 的新版堆利用语境与 tcache/fastbin 相关文章

核心问题：

  • 新版 glibc 对单链表指针做了异或保护
  • 不能再像旧版那样直接写一个裸地址到 fd/next

比赛时要先想三件事：

  • 能不能泄露堆基址
  • 能不能推导受保护指针的真实编码
  • 能不能换用不依赖单链表裸指针的打法

结论：

  • 没堆地址泄露时，safe-linking 题会明显难很多
  • 一旦有 heap leak，很多 tcache/fastbin 利用又会重新可做

现场速记：

  • 先拿 heap leak
  • 再确认保护指针的编码关系
  • 不能硬写裸地址就换成“先泄露、后编码、再投毒”的打法

2.1.6 UAF / Double Free 常见利用链

常见路线：

  • UAF -> heap leak -> libc leak -> tcache poisoning
  • double free -> fastbin/tcache dup -> arbitrary alloc
  • UAF -> smallbin/largebin metadata corruption

比赛判断口诀：

  • 先看能不能重复 free
  • 再看 free 后是否还能 edit/show
  • 最后看能不能把利用链导向“任意分配”或“任意写”

一条常见落地链：

  • show 泄露 heap/libc
  • edit 篡改 tcache/fastbin
  • malloc 拿到目标地址
  • 覆写函数指针、IO 结构或别的控制点

2.2 IO_FILE 利用

2.2.1 FSOP

来源：站内已有《FSOP》。

核心思路：

  • 劫持 _IO_list_all
  • 伪造 _IO_FILE
  • 控制 vtable 中关键函数指针
  • 借助 exit / abort / main return 过程中对 IO 的刷新触发利用

旧版关键条件：

功能说明：

  • 这是触发 _IO_OVERFLOW 链路前常见需要满足的状态条件

使用说明：

  • 比赛里不要只背条件，要同时确认目标 glibc 版本
  • 高版本通常不能照搬老版 FSOP 结构

要点：

  • 本质仍然是劫持函数指针调用链
  • 利用入口通常落在 _IO_flush_all_lockp
  • 高版本要额外考虑 vtable check

2.2.2 IO check

来源：站内已有《IOCheck》与《House-of-apple2》相关内容。

这里建议比赛时先判断：

  • glibc 是否高于 2.24
  • 普通 vtable 是否被校验
  • wide vtable 是否仍可控

2.2.3 House of Apple2

来源：站内已有《House-of-apple2》。

核心点：

  • glibc 2.24+ 的普通 _IO_JUMPS 检查加强
  • 但 _wide_data->_wide_vtable 对应链路没有同等级检查
  • 可通过 _IO_wfile_overflow -> _IO_wdoallocbuf -> _IO_WDOALLOCATE
    这条链进入可控函数指针

常见伪造要点：

  • _wide_data 指向可控区域
  • _IO_write_base == 0
  • _IO_buf_base == 0
  • _wide_vtable 指向可控区域
  • doallocate 指向目标劫持地址

2.3 Hook / 函数指针 / 执行流劫持

2.3.1 malloc_hook / free_hook

功能说明：

  • 这是旧版 glibc 堆题里最常见的收尾点
  • 一旦能把分配结果打到这些 hook 附近，就能在后续 malloc/free 时劫持执行流

使用说明：

  • 先确认远程 glibc 版本，避免比赛时走一条已经被版本淘汰的路
  • 现在更建议把它当成“老版本优先尝试项”，而不是默认答案

常见思路：

  • __malloc_hook -> one_gadget
  • __free_hook -> system
  • 配合 "/bin/sh" 或可控参数触发

2.3.2 exit / atexit / IO cleanup

来源：站内《FSOP》。

比赛里要有这个意识：

  • 有时不必显式调用目标函数
  • 只要能把状态拖进 exit 路径，glibc 自己就会替你触发链路

2.4 版本意识

  • 老版本更常见 __malloc_hook / __free_hook
  • 新版本这些点逐渐消失
  • 新版堆题要更重视：
    • tcache
    • safe-linking
    • IO_FILE 新链路
    • 退出流程 / callback / vtable 旁路

一个实战分界线：

  • 旧版思路更偏 hook/unsorted/fastbin
  • 新版思路更偏 tcache/largebin/safe-linking 绕过/IO_FILE

比赛里的最小判断流程：

  1. 先 checksec 和拿 glibc/libc.so.6
  2. 判断有没有 tcache
  3. 判断单链表有没有 safe-linking
  4. 判断 hook 是否还是现实目标
  5. 如果常规堆链不好走，立刻考虑 IO_FILE 或退出路径

2.5 高版本 glibc 攻击面总览

补充来源：

  • Roderick: https://www.roderickchan.cn/zh-cn/2023-03-01-analysis-of-glibc-heap-exploitation-in-high-version/

功能说明：

  • 这一节用于补齐高版本 glibc 的整体攻击面
  • 重点不是某一个 payload，而是“高版本环境下还有哪些入口能打”

使用说明：

  • 这篇总结主要讨论的是作者写作时仍然成立的高版本技巧，重点覆盖 glibc 2.35 到 2.37
  • 你在线下比赛里要把它当成“攻击面地图”，不是每一项都要背 payload

2.5.1 先记住高版本改了什么

比赛里要先有这个版本意识：

  • glibc 2.32 引入单链表指针保护，tcache/fastbin 直接写裸地址变难
  • glibc 2.33 加强 tcache 数量相关检查
  • glibc 2.34 移除 __malloc_hook / __free_hook，同时对 tcache key 检查更敏感
  • glibc 2.36 以后，部分老 IO 利用链被削弱
  • glibc 2.37 继续缩窄一些老打法，例如 global_max_fast 相关利用面

一句话理解：

  • 高版本不是“没法打”，而是“默认答案从 hook 变成了攻击面组合”

2.5.2 Tcachebin 攻击面

2.5.2.1 绕过指针保护

核心思想：

  • safe-linking 保护的是单链表指针，不是彻底消灭利用
  • 一旦你有泄露，仍然可以恢复或伪造链表编码

比赛直觉：

  • 先找 heap leak
  • 再看 tcache 链里能不能恢复真实地址
  • 最后再考虑 poisoning 或把链导到关键结构

2.5.2.2 劫持 tcache_perthread_struct

功能说明：

  • 这是高版本里非常重要的目标结构
  • 如果你能把分配流程导向这个结构，就相当于接管了某些 tcache 分配行为

使用说明：

  • 常通过 tcache stash unlink 或 largebin attack 这类“写原语”去碰它
  • 这类打法往往不是一步到位，而是先构造任意写，再改这里

2.5.2.3 修改线程局部 tcache 变量

核心思路：

  • 在线程本地存储区域里有 tcache 相关变量
  • 如果能利用 largebin attack 一类写原语改到这些变量，就能影响后续分配行为

比赛意义：

  • 高版本利用里，真正值钱的不一定是直接拿 shell 的点
  • 很多时候是先改 allocator 的关键变量，再把分配劫持成你想要的样子

2.5.2.4 修改 mp_ 结构体

重点变量：

  • tcache_bins
  • tcache_count
  • tcache_unsorted_limit

比赛作用：

  • 改 tcache_bins，可以扩展哪些大小的 chunk 会走 tcache
  • 改 tcache_count，可以影响每条链里允许缓存的数量
  • 改 tcache_unsorted_limit，可以影响 unsorted bin 遍历与预填充过程

实战理解：

  • 这类打法不是传统“直接改 hook”
  • 而是去改 allocator 的“参数面板”，让后续 malloc/free 的行为对你有利

2.5.3 Fastbin 攻击面

2.5.3.1 House of Corrosion

功能说明：

  • 这是高版本里仍然值得记住的 fastbin 技巧之一

使用说明：

  • 这条路线的版本敏感度很高
  • 文中强调它主要能用在 glibc 2.35 到 2.37 一段；进入更后面版本后，相关可控范围会明显缩小

比赛建议：

  • 如果题目环境正好卡在这一段版本，并且能碰到 fastbin/global_max_fast 相关状态，就值得回想这一条

2.5.3.2 Tcache Reverse Into Fastbin

核心思路：

  • 通过构造 fastbin 到 tcache 的转移过程，把某个地址写入目标位置，并且进一步把分配结果导向目标地址

比赛时要注意：

  • 对齐检查更严格，目标地址尾部通常要满足对齐要求
  • 有些写入位置会得到一个 libc 地址或 tcache_key，这本身也可能成为利用点

一句话记忆：

  • 这是“借 tcache 回填流程，把 fastbin 利用扩展成定向写 + 定向分配”

2.5.4 Smallbin 攻击面

2.5.4.1 House of Lore

当前结论：

  • 高版本里这条思路并没有彻底失效
  • 但你需要同时满足链表完整性、对齐、以及 tcache stash 路径上的额外条件

比赛建议：

  • 如果你已经能控制 smallbin 双向链表，就不要轻易放弃 house of lore
  • 只是它一般比老版本写法更讲究布局和前置条件

2.5.4.2 Tcache Stash Unlink Attack

核心意义：

  • 这是高版本非常值得熟记的一条实战链
  • 因为它同时兼具“写地址”和“任意分配”的潜力

可以把它分成两种理解：

  • TSU
    主要效果是向任意地址附近写入一个 libc 地址
  • TSU+
    不仅能写，还可能把目标地址正式链入 tcache，从而实现分配到目标地址

比赛价值：

  • 当老 unsorted / hook 路线不顺时，它经常是高版本题目的中间突破口

2.5.5 Largebin 攻击面

2.5.5.1 Largebin Attack 的定位

高版本里要把 largebin attack 当成“写原语制造器”来看：

  • 它往往不是终点
  • 它非常适合拿来改关键变量、关键指针、线程局部结构
  • 然后再接 tcache、IO_FILE、rtld 等后续链条

比赛直觉：

  • 大 chunk
  • 可改链表指针
  • 旧打法被卡

这三个条件一出现，就应该立刻联想到 largebin

2.5.5.2 House of Husk

文中的结论是：

  • 这条路线依旧可用，但通常需要格式化字符串等额外原语配合
  • 而且往往不是“一次就成”，更偏组合型利用

比赛建议：

  • 把它视作“高版本里 heap 与格式化字符串的联动打法”

2.5.5.3 libc/ld 上的关键变量

高版本里，真正值得你盯住的常常不是传统 hook，而是：

  • libc 上的重要全局变量
  • ld 地址空间上的保护变量和控制变量
  • 与 IO、tcache、pointer_guard、动态链接器状态有关的对象

实战理解：

  • largebin attack 的价值之一，就是帮你把写原语送到这些位置

2.5.6 IO_FILE 攻击面

2.5.6.1 House of Kiwi

结论：

  • 这条利用链在更高版本中受到了明显破坏
  • 尤其是 glibc 2.36 之后，依赖旧 __malloc_assert 行为的打法不再可靠

比赛建议：

  • 如果题解里还是老链条，先别急着照抄，先确认版本

2.5.6.2 House of Emma

核心点：

  • 只要 _IO_cookie_jumps 相关面还在，这条方法就仍有意义
  • 但往往会碰到 pointer_guard 的问题，而它可能位于 ld 空间

比赛直觉：

  • 不只是要伪造结构
  • 还要解决指针保护、地址空间和可写性问题

2.5.6.3 House of Obstack

结论：

  • 即便某些旧入口被删，相关调用链并没有完全消失
  • 高版本里它仍可围绕 obstack 相关路径继续思考

比赛意义：

  • 看到 printf、缓冲刷新、obstack 一类代码时，不要下意识觉得和堆利用无关

2.5.6.4 House of Apple1 / Apple2 / Apple3

比赛里可以这样记：

  • apple1
    更像配合型技巧，可辅助实现定向写入
  • apple2
    重点在于 _wide_vtable 相关检查不完整，从而调用可控函数指针
  • apple3
    关注点是如何绕过指针保护并继续走到函数调用

对你现在最有价值的理解是：

  • 高版本 IO_FILE 不是死了，而是重心从“普通 vtable”转到“wide_data / 特定跳表链路”

2.5.6.5 House of Lyn / Snake

核心认识：

  • 某些 obstack 路径内部仍然会调用函数指针
  • 这类打法说明，高版本利用里“函数指针调用链”依然是核心资产

2.5.7 _rtld_global 与动态链接器攻击面

2.5.7.1 House of Banana

比赛意义：

  • 这是把攻击面继续推向动态链接器内部状态的代表路线

2.5.7.2 link_map

核心认识：

  • 一旦你能碰到动态链接器相关结构，就不只是 libc 内部对象可打
  • 还能利用装载器的数据结构做更深层次的执行流控制

对线下比赛的启发：

  • 当传统 heap -> hook 思路失效时，要学会把视野从 malloc 本身扩展到 ld.so

2.5.8 libc.got / malloc_printerr / 其他侧门

文中提醒了两个很重要的视角：

  • 不要只盯一个目标点
  • 高版本里很多可打位置藏在错误处理、IO 路径、libc.got 这类非传统入口里

比赛建议：

  • 如果程序能稳定触发报错路径，就想想 malloc_printerr
  • 如果能碰到 IO 相关对象，就想想 libc.got in IO

2.5.9 heap_info / malloc_state

这一类结构的价值在于：

  • 它们控制 allocator 的运行状态
  • 一旦能写进去，往往不是直接拿 shell，而是能把整个堆管理逻辑扭向对你有利的方向

比赛理解：

  • 高版本题里，很多强利用并不是“覆写一个函数指针”
  • 而是“先改管理状态，再让程序自己把结果送给你”

2.5.10 __environ 与环境变量面

文中的提醒很实用：

  • 某些环境变量会直接影响 ptmalloc 初始化
  • 一些环境信息还可能成为泄露入口

比赛里要记住：

  • GLIBC_TUNABLES 可能改变 tcache 相关配置
  • 一些环境变量可能协助信息泄露或影响利用稳定性

2.5.11 Other

还值得记住这些零散但重要的方向：

  • house of muney
    更偏 mmap chunk 相关技巧
  • exit 路径上的函数指针
    很多利用并不需要你显式 call，只要能把程序拖进退出链就可能触发
  • tls_call_list 一类退出阶段对象
    依赖更强的前置条件，但属于高版本仍值得知道的攻击面

2.5.12 这一篇文章对比赛最有用的结论

如果只保留最核心的经验，可以记这几条：

  • 高版本堆题的答案通常不是单点，而是“泄露 + 写原语 + 关键结构劫持”的组合
  • largebin attack 的价值非常高，因为它经常负责造出后续利用所需的写原语
  • tcache_perthread_struct、线程局部 tcache 变量、mp_、IO_FILE、rtld 结构都应纳入目标列表
  • hook 被移除后，真正应该学会的是“找 allocator 和 runtime 里还剩哪些控制面”
  • 比赛现场不要死背名字，要先问自己：我现在有的是泄露、任意写、任意分配，还是只改一个指针的能力

3.1 House of Spirit

原文范围：2.23-至今

漏洞成因：

  • 堆溢出
  • UAF
  • 能伪造 fake chunk 并让其参与回收

适用范围：

  • 老版本常见于 fastbin
  • 引入 tcache 后，也能在对应大小类上演化出类似思路

利用原理：

  • 在目标地址伪造一个看起来合法的 chunk
  • 通过 free 把这块假内存送进 allocator
  • 再通过 malloc 把它重新取出来

相关技巧：

  • 重点是 fake chunk 的对齐和 size 合法性
  • 通常要保证相邻位置也能通过基本检查

利用效果：

  • 任意地址分配
  • 栈上分配
  • 全局区分配

3.2 House of Einherjar

原文范围：2.23-至今

漏洞成因：

  • off-by-one
  • off-by-null
  • 能修改 prev_size 或清掉 prev_inuse

适用范围：

  • 需要程序布局允许后向合并
  • 常见于相邻 chunk 比较规整的题

利用原理：

  • 利用边界破坏伪造前一块 chunk 的状态
  • 在 consolidation 时把一段本不该合并的区域并进去
  • 由此制造 overlapping chunk

相关技巧：

  • 经典入口是空字节溢出
  • 需要同时关注 fake chunk 布局与 next chunk 状态

利用效果：

  • overlapping chunk
  • 间接改写别的 chunk 内容或元数据

3.3 House of Force

原文范围：2.23-2.29

漏洞成因：

  • 堆溢出到 top chunk
  • 能改 top chunk size

适用范围：

  • 需要能持续控制后续 malloc 申请大小
  • 经典思路主要适用于老版本

利用原理：

  • 把 top chunk size 改到极大
  • 精确计算下一次申请的偏移
  • 让新的 chunk 落到攻击者想要的位置附近

相关技巧：

  • 本质是 top chunk 偏移计算题
  • 不依赖 free

利用效果：

  • 任意地址附近分配
  • 覆写全局变量、hook、结构体

3.4 House of Lore

原文范围：2.23-至今

漏洞成因：

  • UAF
  • edit after free
  • 能操作 smallbin 双向链表

适用范围：

  • 需要进入 smallbin
  • 高版本下还要考虑 tcache stash 流程和对齐限制

利用原理：

  • 构造或伪造 smallbin 双向链关系
  • 让 malloc 从链表里返回攻击者准备好的位置

相关技巧：

  • 要满足链表一致性约束
  • 需要关注 victim->fd->bk == victim 一类检查

利用效果：

  • 任意位置分配
  • 给后续任意写或结构劫持做跳板

3.5 House of Orange

原文范围：2.23-2.26

漏洞成因：

  • 可以控制 top chunk
  • 程序可能没有显式 free

适用范围：

  • 适合“无 free 但能持续申请”的环境
  • 更偏老版本链路

利用原理：

  • 先操控 top chunk
  • 当新的大申请无法由当前 top 满足时，原 top 会被处理进 unsorted bin
  • 再利用 unsorted bin 与 IO_FILE 链条继续推进

相关技巧：

  • 关键思想是“人造 free”
  • 后续常接 FSOP

利用效果：

  • 任意写
  • IO_FILE 劫持
  • 代码执行

3.6 House of Rabbit

原文范围：2.23-2.28

相关技巧：

3.8 House of Storm

原文范围：2.23-2.29

漏洞成因：

  • 堆溢出
  • UAF
  • edit after free

适用范围：

  • 可以做 unsorted bin attack
  • 可以做 largebin attack
  • 可以分配 0x50 大小的 chunk

利用原理：

  • 这是一个组合型技巧
  • 借 PIE 程序堆地址常见的开头特征，先用一次 largebin attack 写两个堆地址
  • 再用一次 unsorted bin attack 写一个 libc 地址
  • 最后把 0x50 的分配结果导向目标地址

相关技巧：

  • 一种常见整理方式是：
    先做一次 unsorted bin attack，把 bk 改到 addr
  • 再做一次 largebin attack，把 bk 改到 addr+0x10，把 bk_nextsize 改到 addr-0x20+3
  • 再申请 0x50 大小的 chunk，把结果拿到 addr
  • 原文还特别提醒：
    某些低位选择会触发断言，实战里成功率会受影响

利用效果：

  • 任意地址分配

3.9 House of Corrosion

原文范围：2.23-至今

漏洞成因：

  • 堆溢出
  • UAF
  • 能污染 fastbin 或与 global_max_fast 相关状态

适用范围：

  • 版本敏感
  • 在高版本中仍有价值，但更依赖组合原语

利用原理：

  • 先污染 allocator 关键状态
  • 再把这种状态污染转化为更强的写能力或分配能力
  • 最终推动到关键目标对象

相关技巧：

  • 常与 global_max_fast、链表组织和多阶段堆风水有关
  • 不适合硬背单个 payload

利用效果：

  • 写原语扩大
  • 任意分配
  • 间接劫持执行流

相关技巧：

  • 更适合和其他方法结合使用

利用效果：

  • 任意地址写堆地址
  • 为后续 Apple2/3 做准备

3.26 House of Apple2

原文范围：2.23-至今

漏洞成因：

  • 能伪造 _IO_FILE_plus
  • 能控制 _wide_data

适用范围：

  • 高版本非常重要

利用原理：

  • 普通 vtable 检查加强后
  • 转向 _wide_data -> _wide_vtable
  • 借 _IO_wfile_overflow 等链路调用可控函数指针

相关技巧：

  • 需要同时准备 heap leak 和 libc leak 会更稳
  • 常和 largebin attack 这类单次强写原语联动

利用效果：

  • 函数指针调用
  • 控制流劫持

3.27 House of Apple3

原文范围：2.23-至今

漏洞成因：

  • 高版本 IO 对象可控

适用范围：

  • 更强保护下的 Apple 路线

利用原理：

  • 延续 Apple 系列思路
  • 在附加保护下继续寻找可达的 IO 调用链

相关技巧：

  • 后续高版本文章指出：
    这条路线关注 shlib_handle 等对象，去绕过指针加密再调用函数指针

利用效果：

  • 控制流劫持

4.4.1 先判断漏洞点

4.4.2 能小修就不要大改

  • 漏洞先失效
  • 服务别挂
  • 数据流别断

  • 增加长度检查
  • 删危险功能
  • 把 free 改空逻辑或阻断危险调用链

  • 对 UAF 置空指针
  • 增加 one-shot 校验

5.ORW

通常使用open read write

open(path, flags, mode) 参数解析

flags

  • 表示“以什么方式打开文件”
  • 它决定你是只读、只写、读写，是否创建文件，是否追加，是否截断等

常见值：

  • O_RDONLY=0：只读，通常是 0
  • O_WRONLY=1：只写
  • O_RDWR=2：读写
  • O_CREAT=64：文件不存在就创建
  • O_TRUNC=512：打开时清空文件
  • O_APPEND=1024：追加写

mode

  • 表示“如果这次打开顺便要创建文件，那新文件权限是多少”
  • 只有在 flags 包含 O_CREAT 这类创建语义时，它才真正有意义
  • 如果不是创建文件，通常直接传 0

常见值：

  • 0644：拥有者可读写，其他人只读
  • 0755：拥有者可读写执行，其他人可读执行

sendfile

原型 ssize_t sendfile(int out_fd, int in_fd, off_t *offset, size_t count);

作用: 在两个文件描述符中直接拷贝数据,不用经过用户态进程空间

out_fd 输出文件描述符,表示拷贝数据的目标

in_fd 输入文件描述符,拷贝数据的源

offset 文件读取的偏移

count 拷贝字节数
