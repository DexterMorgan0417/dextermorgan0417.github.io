第 1 章 引言

软件正在深刻改变我们的生活和工作方式：我们通过智能手机和社交媒体与朋友沟通，通过网站购物和获取知识；在工作中，软件帮助企业组织业务、触达客户并形成竞争优势。

但高质量软件仍然很难构建，现实中的大量软件都带有 bug 和安全漏洞。书中举了若干例子：丰田汽车失控加速、Nest 智能温控故障导致住户失去供暖、竞态条件引发的美国东北部停电，以及 Therac-25 放疗设备的致命事故。

程序分析的核心目标，就是通过分析程序代码来获知其性质。它可以帮助我们发现漏洞、生成测试、自动修复软件，并支持编译优化。

本书的整体路线是：先用数学形式化方法描述程序如何执行，再说明编译器和分析工具如何表示程序，接着讲数据流分析与抽象解释，最后扩展到指针分析、过程间分析、符号执行等更高级的话题。

一句话总结：程序分析既有深厚的数学基础，也有很强的工程实用性。

第 2 章 WHILE 语言与程序表示

这一章先构造一个足够小、足够干净的玩具语言 WHILE，然后把它变形成更适合程序分析的中间表示 WHILE 3ADDR。

2.1 WHILE 语言

WHILE 是一个极简命令式语言，包含赋值、skip、顺序执行、if、while，以及整数表达式和布尔表达式。

书里用元变量来区分语法类别：S 表示语句，a 表示算术表达式，b 表示布尔表达式，x/y 表示程序变量，n 表示数字常量。

先引入这种玩具语言的原因，是为了避开真实语言复杂的语法细节，只保留顺序、分支、循环这些程序分析最核心的结构。

2.2 WHILE 3ADDR

对程序分析来说，源码形式的 WHILE 仍然不够规整。表达式可能嵌套，语句和布尔表达式也各有不同形式，因此书中把它改写成更低层、更规则的三地址码。

例如 w = x * y + z 会拆成两条指令：先乘出临时变量，再做加法。核心思想是把复杂结构拆成分析更容易处理的小原语。

控制流也会降级为条件跳转和无条件跳转，于是程序可以被看成“地址到指令的映射”。这一步是后续几乎所有静态分析的前提。

2.3 扩展 与 2.4 CFG

在真实分析框架中，WHILE 3ADDR 还会继续扩展出函数调用、返回、方法调用、取地址、解引用、字段读写等构造。

第 3 章 程序语义

这一章回答的问题是：程序“执行”的含义如何被精确定义。书中采用操作语义作为主要工具。

3.1 操作语义

操作语义描述程序如何执行，核心分为两类：大步语义与小步语义。

  • 大步语义：直接描述一个表达式或语句最终得到什么结果。
  • 小步语义：把执行拆成一步一步的状态迁移。

在 WHILE 语言里，大步语义很像解释器的数学版定义；它简洁，但看不到中间过程。小步语义更像逐帧动画，能清楚展示中间状态、控制流重写和多步执行关系。

到了 WHILE 3ADDR，程序已经不再是语法树上的复合语句，而更像“编号指令表”，因此语义配置里必须显式加入程序计数器，表示下一条要执行的指令。

3.2 推导、可证明性与归纳

一旦有了推理规则，我们就能把规则实例串成推导树，证明某个判断成立。由此又引出可靠性、完备性以及归纳证明，尤其是结构归纳。

如果你读这一章很吃力，通常不是因为不会，而是同时在消化符号系统、状态概念、推理规则和归纳证明。建议先只抓四个关键词：状态、配置、规约、推导。

本章最重要的记忆点

  • 大步语义关心最终结果。
  • 小步语义关心逐步执行。
  • WHILE 3ADDR 语义需要显式程序计数器。
  • 推理规则和推导树，是后续证明分析正确性的语言基础。

第 4 章 面向 WHILE 3ADDR 的数据流分析框架

这一章开始回答：我们怎样在不真正运行程序的前提下，推断程序在各个点上可能具有的性质？答案就是数据流分析。

数据流分析通常需要定义三样东西：抽象域、传递函数、合流操作。抽象域决定你跟踪什么信息，传递函数决定指令如何改变信息，合流操作决定多条路径汇合时怎样合并信息。

在直线代码里，信息可以顺着控制流传播；遇到分支后，就要把不同路径的信息合并。遇到循环后，分析往往要反复迭代，直到达到稳定点。

Join 是这章的核心概念。不同路径流来的抽象信息必须通过 join 合并成统一结果。join 会损失精度，但换来了可计算性。

第 2 到第 4 章精讲版

一条总主线

这三章其实在回答三个连续的问题：程序长什么样，程序执行是什么意思，不真正执行程序能不能推断它的性质。

第 2 章解决第一个问题，第 3 章解决第二个问题，第 4 章解决第三个问题。把这条线抓住，整本书会顺很多。

第 2 章精讲：为什么一定要先有 WHILE 和 3ADDR

很多初学者会问，为什么不直接分析 C 或 LLVM IR。原因是课程要先讲原理，而不是一上来就被工业细节淹没。

WHILE 的作用是把程序缩成最小核心：变量、表达式、赋值、分支、循环。只要这几个东西讲清楚，后面的语义和分析框架就有了最小工作样本。

但 WHILE 还不够适合分析，因为它的表达式嵌套太自由。分析更喜欢一种每一步都很小、形式统一的程序表示，这就是 3ADDR。

例如表达式 w = x * y + z 会先算出一个临时变量，再把临时变量与 z 相加。这样每条指令的影响都很局部，后面定义语义、定义传递函数、做数据流分析都会简单很多。

第 2 章里最容易忽略的一点：CFG 不是执行轨迹

CFG 表示的是程序可能怎样走，而不是程序某次实际怎样走。真实运行时 if 语句只会走一个分支，但 CFG 必须同时保留两个分支，因为静态分析分析的是所有可能输入下的程序。

第 3 章精讲：为什么要有两种语义

大步语义和小步语义不是谁替代谁，而是服务不同问题。大步语义更像在回答这段程序最后算出了什么，小步语义更像在回答这段程序是一步一步怎么走到结果的。

例如顺序语句 x = 1; y = x + 2，大步语义会更像直接说最终状态里 x 等于 1，y 等于 3。小步语义则会把执行拆成先完成第一条赋值，再完成第二条赋值的多次状态迁移。

所以，大步语义适合讲结果，小步语义适合讲过程。课程后面为什么更偏爱小步，是因为分析、证明、控制流、程序点这些概念，本质上都和过程更贴近。

配置到底是什么

配置就是程序执行到某一刻时，机器手上掌握的全部必要信息。

在 WHILE 里，配置通常是当前状态加当前语句。在 3ADDR 里，配置通常是当前状态加当前程序计数器。这解释了为什么 3ADDR 语义里必须显式加入 PC。

第 3 章最难点：推导树不是装饰，而是证明本身

推理规则不是形式化记号堆砌。推导树就是为什么某个结论成立的完整证据。后面静态分析正确性，本质上也是在证明分析算出来的东西和真实语义之间满足某种可靠关系。

第 4 章精讲：数据流分析到底在干什么

最容易把数据流分析想错成模拟程序运行。其实它不是。它做的是：在每个程序点上维护一个抽象信息，并沿 CFG 传播它。

比如你可以跟踪某个变量是不是常量，某个变量可能是正数负数还是未知，某个定义是否能到达这里，某个变量在后面会不会再被使用。这些都不是具体值，而是关于值的抽象事实。

为什么必须要 join

看一个简单例子：如果 cond 为真时 x 赋值 1，否则 x 赋值 2，那么在 if 之后，静态分析面对的是两条可能路径的合并结果。这个合并动作就是 join。

对常量传播来说，1 和 2 合并后通常不再是一个精确常量；对符号分析来说，它们可能仍然都属于正数。join 的本质就是用精度换可计算性。

为什么循环会导致迭代

因为循环意味着信息会回流。一个程序点的输出又会影响它自己之后的输入，所以分析不能只算一次，必须反复传播直到不再变化。这就是固定点计算的直觉来源。

你现在最该掌握的三个图景

  1. WHILE 是语义教学模型。
  2. 3ADDR 和 CFG 是分析工作模型。
  3. 数据流分析是在 CFG 上传播抽象信息并求稳定解。
